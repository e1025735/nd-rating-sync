# nd-rating-sync — project context

Navidrome plugin (WASM) that reads embedded star-rating tags from MP3, FLAC, Ogg-Vorbis, Opus, WAV, DSF, M4A/AAC and WMA files and writes them to Navidrome via the Subsonic `setRating` API. Navidrome doesn't import embedded ratings on its own; this plugin bridges file tags and the Navidrome user-rating system.

## Build

Must be built with **TinyGo** targeting `wasip1`:

```
tinygo build -o plugin.wasm -target wasip1 -buildmode=c-shared .
zip -j nd-rating-sync.ndp manifest.json plugin.wasm
```

`make build`, the release workflow and the Renovate bump workflow all run this same command (`make` also rebuilds on any change under `internal/`). Keep them in sync.

- `-gc` is left at the target default (`conservative`). `leaking` would never free memory and a full sweep would run out of heap.
- `-panic` stays at the default `abort`, which prints the panic message (`trap` prints nothing). Panics cannot be recovered on WebAssembly anyway, so the message is the only clue.

`go test ./...` and `go vet ./...` work on the regular toolchain (CI runs both, and runs the tests a second time as `GOARCH=386` so size arithmetic that only overflows with a 32-bit `int`, as assumed for TinyGo on wasip1, is caught; untrusted sizes are compared as `uint64` before narrowing to `int`). `pdk_stub.go` and `internal/logging/logging_stub.go` are `//go:build !wasip1` and provide no-op stand-ins for `getConfig` and the log functions; the Navidrome PDK ships matching non-wasip1 stubs for `host.*` (incl. `host.LibraryMock` for `LibraryGetLibrary` and `host.MatcherMock` for `MatcherMatchSongs`). Only `GOARCH=wasm GOOS=wasip1 go vet ./...` fails — host imports have no Go function bodies under wasip1; TinyGo wires them up at link time. That part is expected.

## File access (matcher + filesystem mount)

Navidrome does **not** hand a plugin an openable path through Subsonic. The
`search3` `path` field is a *synthesized fake* (`AlbumArtist/Album/NN-NN -
Title.ext`, see Navidrome's `server/subsonic/helpers.go::fakePath`) unless the
plugin's player has Report Real Path enabled — which a plugin cannot set. So the
plugin ignores `s.Path`, asks Navidrome's **matcher** for each song's real path
and reads the file through the library **mount**:

- Requires **Navidrome ≥ 0.63.0** (the matcher host service; a module importing
  `matcher_matchsongs` cannot even be loaded by older servers). The PDK is pinned
  to the v0.63.0 commit so no newer host function is used by accident.
- `manifest.json` declares `"library": { "filesystem": true }` and `"matcher"`.
  Navidrome then read-only-mounts each assigned library at `/libraries/{id}`
  inside the sandbox, and the matcher fills `Track.Path` only because filesystem
  access is granted.
- `hostLookups.mount(libraryId)` → `host.LibraryGetLibrary(int32(id))` (`MountPoint`
  and the host root `Path`). `libraryId` must be numeric; a blank/non-numeric ID
  or empty `MountPoint` (filesystem perm not granted / library unassigned) is
  logged and the (library, user) is skipped without touching any rating.
- `locateSongFiles` sends the page's song IDs (as `types.SongRef{ID}`) to
  `host.MatcherMatchSongs` in one call. The matcher looks IDs up exactly first;
  with only an ID there is nothing for its MBID/ISRC/fuzzy stages to match, so a
  song that is gone comes back `nil`. Results are in input order.
- `Track.Path` is Navidrome's `media_file.path`, **relative to the library
  root** (`MediaFile.AbsolutePath()` = `LibraryPath` + `Path`).
  `relativeTrackPath` also accepts an absolute path below the host root and
  converts Windows backslashes when the host root shows a Windows host; a path
  that would leave the root is rejected. The file is `path.Join(MountPoint, rel)`
  and its mtime comes from `os.Stat` on it.
- No track / another ID / `Missing` / another library / empty path / outside the
  root / not in the mount → `songFile{found:false, reason}` → the caller counts
  `skippedUnreadable` (never `tagAbsent`) and warns with the reason, so such a
  file can never be cleared by `clear_rating_if_untagged`.
- A failed matcher call counts an attempt like a failed `search3` page (see
  *Sync execution*).
- There is **no** host "read file" API; `readAudioMetadata` uses plain `os.Open`
  on the located mount path.
- `OnInit` deletes the file index that versions ≤ 0.22 kept in the KV store
  (`PurgeLegacyFileIndex`).

## Config model

Config is a hierarchical JSON Schema (not a flat key-value list):

- Top-level admin scalars read via `pdk.GetConfig`: `sync_schedule` (defaults to hourly `0 * * * *` — idle runs are cheap thanks to the LastScanAt gate, so a frequent schedule is fine), `incremental_sync` and `dry_run` (there is no song cap — chunking + the `callBudget` keep runs safe; see **Sync execution**)
- Top-level admin tristate defaults (also via `pdk.GetConfig`): `default_skip_already_rated`, `default_clear_rating_if_untagged` — each a `*bool` in `pluginConfig`; `nil` = no admin default
- `libraries` array read via `pdk.GetConfig("libraries")` as a JSON string, then unmarshaled:
  - Each library: `libraryId`, `libraryName`, `users[]`
  - Each user: `username`, `skip_already_rated` / `clear_rating_if_untagged` (both tristate `*bool`); resolved via `resolveTristate(user, admin, fallback)` (fallbacks: skip `true`, clear `false`), `ratingTagOrder`

`CONFIG_EXAMPLES.md` documents, per setting combination, what happens to a song (the outcome tables follow `processSong`), plus example setups in admin-page terms. Keep it in sync when the per-song pipeline or a setting changes.

### Config-change invalidation

**Incremental thresholds** are never purged by a config change. Each `last-synced` value carries a fingerprint of its own pair's `ratingTagOrder`, `skip_already_rated` and `clear_rating_if_untagged` (`pairFingerprint`); a threshold saved with other settings reads as "none", so that pair's next sweep reads every file once. Values written by older versions have no fingerprint and are accepted as they are.

## Supported tag formats

`ratingTagOrder` values are *source applications*, not container-specific keys. Each source maps to whatever tag(s) that application writes in each container. FLAC, Ogg-Vorbis and Opus all share the Vorbis comment format, so they use the same column.

| `ratingTagOrder` key | MP3 / WAV / DSF / ADTS `.aac` (ID3v2) | FLAC / Ogg / Opus (Vorbis) | M4A / AAC (MP4 atom) | WMA (ASF) | Scale |
|----------------------|-------------------------|----------------------------|-----------------------|-----------|-------|
| `"WMP"` | POPM ("windows media player") | — | — | `WM/SharedUserRating` DWORD (WORD also accepted) | POPM: non-linear fixed points (1/64/128/196/255). WMA: 0–99 (WMP writes 1/25/50/75/99), ranges 1–12/13–37/38–62/63–87/88–99 → 1–5 stars; >99 = unrated |
| `"iTunes"` | POPM ("itunes" / "com.apple.itunes") | — | `rating` freeform (lowercase) | — | Linear 0–100 (20/40/60/80/100). iTunes-style tags written by other tools — iTunes/Apple Music keep ratings in their library database and never write them to the file |
| `"MediaMonkey"` | POPM ("no@email", MediaMonkey's own frame), else TXXX `FMPS_Rating` | `RATING` (0–100), else `FMPS_RATING` | `rate` freeform (any case), else `FMPS_Rating` freeform | `FMPS_Rating` Unicode | POPM: exact whole-star bytes 1/64/128/196/255 (+ MediaMonkey 3.x 23/252); `RATING`/`rate`: 20/40/60/80/100; FMPS: whole stars only (0.2 steps) |
| `"foobar2000"` | TXXX `RATING`, else the WMP POPM frame (foobar2000 writes its RATING to MP3 as POPM "Windows Media Player 9 Series") | `RATING` | `RATING` freeform (uppercase) | — | Integer 1–5 (0/empty = no rating, anything else is not a whole star); the POPM fallback uses the WMP ranges |
| `"MusicBee"` | POPM ("musicbee", exact whole-star bytes 1/64/128/196/255) | `RATING` | `RATE` freeform (any case) | `WM/SharedUserRating` (same as WMP) | `0/20/40/60/80/100` → 1–5 stars; half-star values (10/30/…/90) and values above 100 are not whole stars |
| `"FMPS"` | TXXX `FMPS_Rating` | `FMPS_RATING` | `FMPS_Rating` freeform | `FMPS_Rating` Unicode | freedesktop FMPS (Strawberry, Clementine, Amarok, …); whole stars only (0.2 steps). The same field stays MediaMonkey's fallback |

Per-user `ratingTagOrder` controls priority; first match in the file wins. The default order (`scanner.DefaultTagOrder`, also the manifest default) is WMP, iTunes, MediaMonkey, foobar2000, MusicBee, FMPS; changing it changes the fingerprint of users without their own order, so their next sweep reads every file once.

Player rating formats are poorly documented. Mappings that cannot be confirmed from a real file are not guessed: e.g. Windows Explorer's M4A `rate` atom has an unknown scale that conflicts with MediaMonkey/MusicBee's 0–100 `rate`, so `WMP` has no M4A mapping until a user reports one with a sample file (README asks for an issue). Sources without a representation in a given container are silently skipped (e.g. `WMP` listed for a FLAC file simply never matches — keeping it in the order is harmless).

**No rating means 0 stars.** A file read to a clean end without a rating from any source in the user's order, or whose rating field is empty or 0, is `TagAbsent`: rated 0, and `clear_rating_if_untagged` sets Navidrome to 0 (only when Navidrome has a rating; skipped-as-rated songs are never read). **A value Navidrome cannot show is not "no rating":** MusicBee/MediaMonkey POPM half-star bytes (13/54/118/186/242) or other unknown bytes, 0–100 values not on a multiple of 20, FMPS values not on a 0.2 step, foobar2000 `RATING` outside 1–5 and `WM/SharedUserRating` above 99 mark the source unusable (`ratings.decoded`); when no source in the order has a whole-star rating, `pickRating` returns `media.ErrNotWholeStar`, the scanner reports `TagNotWholeStar` and `processSong` skips the song (`skippedNotWholeStar`) without writing or clearing. A later source with a whole-star rating still wins. MusicBee/MediaMonkey POPM must be decoded by exact value, not by range — their ½★ byte (13) is larger than their 1★ byte (1). WMP and iTunes POPM keep range decoding. MediaMonkey's own field wins over an `FMPS_Rating` in the same file; in WMA MediaMonkey is only read from `FMPS_Rating` (its native WMA field is unverified).

`ratingFromVorbisComments` (in `flac.go`) is the shared resolver used by the FLAC and Ogg/Opus paths — extending Vorbis-side tag detection means editing it once.

## Incremental sync

When `incremental_sync` is true (default), each (library, user) tuple records the wall-clock time of its last successful scan in the Navidrome KV store and skips songs whose file mtime predates it.

- KV key: `last-synced:{libraryID}:{username}` (plugin-scoped by the host).
- Value: scan-start timestamp plus the pair fingerprint (`"<RFC3339Nano> <fingerprint>"`, see *Config-change invalidation*), the timestamp captured when the pair *starts* (carried as `SyncCursor.PairStart` across continuations) and written only when the pair is **fully** processed — so an interrupted/resumed sweep never advances the threshold past songs it hasn't reached yet. RFC3339Nano UTC.
- Skip rule: the located file's `ModTime().Before(threshold)` (from the `os.Stat` in `locateTrack`) — exact-equality files re-process, which keeps `setRating` idempotent and avoids drift if mtime resolution is coarser than expected.
- New-song override: a song whose Subsonic `created` is at/after the threshold is processed even with an old mtime (`songAddedSince` in `song.go`). A renamed/moved file keeps its mtime but Navidrome imports it as a new, unrated song; without this it would be skipped forever. A missing/unparseable `created` falls back to the plain mtime rule.
- Failure modes are non-fatal: a missing/malformed/unreadable KV value falls back to "no threshold" (full scan); a KV write failure means the next run does redundant work, never incorrect work.
- Known blind spots, documented for users (HOW_TO_SETUP, "Incremental sync and file times") rather than handled in code: the threshold is host-clock time while the mtime comes from the file server or the SMB client that wrote the tag, so a clock behind the host, a wrong timezone or a DST shift can make a changed file look older than the threshold; and a tagger that preserves the mtime hides the change from Navidrome and the plugin alike. No safety margin is applied on purpose; the cure is one run with `incremental_sync=false`.
- Changing a user's `ratingTagOrder`, `skip_already_rated` or `clear_rating_if_untagged` invalidates that pair's threshold automatically (fingerprint). Set `incremental_sync=false` to force a full scan every run, e.g. for debugging.

### LastScanAt gate (skip unchanged libraries)

Incremental sync skips per-*file* work but still pages the whole `search3` listing. The gate (in `runSyncChunk`, helper in `library.go`) eliminates the listing too: when starting a **fresh** pair, it compares the library's `LastScanAt` (`host.LibraryGetLibrary`, unix seconds) against the stored `last-synced` threshold and, if `lastScan.Before(threshold)` (Navidrome hasn't rescanned since our last sweep), **skips the entire pair** with no paging.

- Gate condition: `cur.Offset == 0 && cur.PairStart == "" && cfg.IncrementalSync && !threshold.IsZero()`. `incremental_sync=false` bypasses it.
- A gated skip **must not save** the threshold — it stays pinned to the last *real* sweep, so when Navidrome eventually rescans, the per-file mtime path still re-processes the files that changed. Reuses the existing `last-synced` value; both `LastScanAt` and `PairStart` are host-clock so comparable. No new KV key.
- `hostLookups.lastScan` fails **open** (returns `(zero,false)` → page) on a non-numeric library ID, host error, or `LastScanAt==0`. Library IDs must be numeric (Navidrome's internal IDs are) for the gate to engage. `hostLookups.library` memoises per call, so N users of one library cost one host call for the gate and the mount lookup together.
- Requires the `library` permission (also what grants the filesystem reads) — the host registers the Library service only when `Permissions.Library != nil`.

| ID | Trigger |
|----|---------|
| `nd-rating-sync-recurring` | Cron-based full sync |
| `nd-rating-sync-immediate` | One-shot at plugin init |

## Sync execution (30s host limit)

Navidrome force-closes any plugin call exceeding **30 s** (`extism.Manifest.Timeout`, hardcoded in the host's `manager_loader.go`; not configurable by the plugin). So no callback may do unbounded work:

- `RunSyncStep` runs one `callBudget` (**15 s** — well below the 30 s host limit; see *Why 15 s* below) slice via `runSyncChunk`, then either finishes (`sync complete`) or reschedules a one-time continuation carrying the `SyncCursor` and returns.
- **No panic recovery in production.** TinyGo cannot `recover()` on WebAssembly: a panic exits the module without running deferred functions (seen by the host as `module closed`). The `recover()` in `parseStars` only protects native builds (`go test`, fuzzing). Code on the sync path must therefore be panic-free by construction — bounds-check every length, compare untrusted sizes as `uint64`, never index without a length check; the media parsers are fuzzed for this.
- The continuation uses an **empty** `scheduleID` so the host mints a unique one — reusing the firing entry's own ID would be rejected as a duplicate (the one-time entry is still registered during its own callback).
- **Each callback is a fresh WASM instance** — Go package globals do NOT persist across calls. All cross-call state must live in the scheduler payload (`SyncCursor`) or the KV store.
- Forward progress is guaranteed: `processPairChunk` checks the deadline after every song, so every callback that reaches a pair's songs advances the cursor by ≥1 song. `setRating` idempotency makes a re-processed song on resume harmless.
- **Pairs that make no progress are bounded.** A failed `search3` page, or a failed matcher lookup of a page, counts an attempt in `SyncCursor.Retry`. Such a continuation is scheduled after `retryDelaySeconds` (30 s, well under `SweepStaleAfter` so the chain still counts as active) instead of immediately; after `maxPairAttempts` (3) the pair is skipped until the next sweep, without saving its threshold. Any processed song resets the counter. Without this, a username Navidrome does not know re-ran back to back forever and blocked every cron sweep through the heartbeat.
- **Paging order.** `search3` with the empty query `""` takes Navidrome's own empty-query path: every song not marked missing, ordered by `media_file.rowid` (insertion order), paged with LIMIT/OFFSET (v0.63 `persistence/sql_search.go`, `doSearch`). New songs land at the end, so nothing shifts; songs that disappear before the cursor's offset during a sweep (deleted, or marked missing by a rescan) shift later songs back, and that many songs are skipped once. Accepted on purpose: it only matters when such a skipped song's file changed before the sweep (the saved threshold then hides it), and the Subsonic API offers no keyset paging to avoid it.
- **One read per song per user.** Pairs run one after another and each reads its own files; tag results are not shared between users of a library. Deliberate trade-off: the gate and the incremental skip keep normal runs cheap, and sharing reads would mean a page-by-page loop across users (cursor, gate, retries and crash recovery all reworked). Only the first import, `incremental_sync=false` and the one re-read after a settings change pay the N× cost.
- **Why 15 s.** Production saw a wazero host-side panic (nil pointer deref in `Context.Walltime`) ~16 s into a callback, then later a 30 s host timeout (`module closed with context deadline exceeded`) when a chunk ran the full wall. Both rooted in chunks running too long. The budget was cut to 10 s and later raised to 15 s; combined with the per-song deadline check it is enforced tightly — even with 2–3 s slow songs we yield within one song of the budget, never approaching the 30 s wall.
- **Continuations fire immediately** (except retries, see above). `SchedulerScheduleOneTime(0, …)` runs as `time.AfterFunc(0, …)` host-side, so the next slice starts at once — a big first import is a *continuous back-to-back chain* (minutes), **not** gated by the cron. The cron interval only governs how often a *fresh* sweep starts; convergence speed comes from the chain.
- **Overlap guard.** Every sweep records/refreshes the `sweep-active` sweep record (`MarkSweepActive(cursor)`) at the start of every callback and every song page; a *fresh* sweep (`!resumed`) bows out if the record is `Active()` — younger than `SweepStaleAfter` (2 min; a future-dated one from a backward clock step counts as stale) and not interrupted. On `done` it calls `ClearSweepActive`. Continuations refresh but never run the in-progress check (so a chain can't block itself). Best-effort (no KV CAS) — idempotency covers the residual fresh-vs-fresh race.
- **Crash recovery.** The record is only deleted when a sweep completes, so a record that is still there means the chain stopped mid-sweep, and the next fresh run resumes at its cursor (`startOrResumeSweep`) instead of starting over. A reload (`OnInit` → `MarkSweepInterrupted`) or a continuation the host refused is marked *interrupted* and simply resumes. Anything else was a crash — a panic, running out of memory or the 30 s limit, after which the plugin cannot log anything — so the sweep resumes at the start of the page it was on with `LogReadsUntil` = end of that page, and `processSong` logs every file as a warning *before* reading it (`pdk.Log` is synchronous, so the line is in Navidrome's log before a crash). If a file crashes the plugin again, it is the last "reading" warning before the stop; the user fixes or removes it — the plugin does not skip it on its own. The next page is read normally again.
